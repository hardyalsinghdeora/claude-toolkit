# Work Log & Reports

## Data — offline script FIRST (zero tokens)

The raw logs are generated by `bin/worklog` (also on PATH as
`worklog`) from the csession index + git commits. Automation keeps them
current, but always start by making sure:

```bash
worklog check            # backfill last 7 days + today (after 21:00)
worklog status           # which days are logged
worklog week             # aggregate 7 days -> Output/worklog/week-<date>.md
worklog generate --date 2026-07-20 --force   # rebuild one day
```

Read the generated files from `Output/worklog/<YYYY-MM-DD>.md` — never
re-derive session/commit data yourself; the script already did it for free.

## What the model adds on top

1. **Daily narrative** — 3–5 sentences: what the day was actually about
   (group the sessions into themes; the titles are per-session, the story
   isn't). Append under `## Summary` in the day's file.
2. **"What could be better" coaching** — expand the auto `## Flags` with
   specific, actionable advice tied to the user's actual patterns (e.g. which
   task pivots deserved a /clear; which one-question sessions could have been
   one batched prompt; repos with edits but no commits).
3. **Reports** — run `worklog week`, then turn the aggregate into the
   requested format (weekly status mail, monthly review, sprint input).
   Frontmatter in each daily file (`date/sessions/commits/transcript_tokens/
   projects`) is machine-readable for exactly this purpose.

## Rules

- Logs live in `Output/worklog/` (gitignored — personal). Never commit or
  post them; reports derived from them also stay in `Output/` unless the
  user explicitly says to send/publish.
- Weekend/leave days have no log by design (no activity ≠ missing log).
- Keep the enriched sections marked (`## Summary`, `## Coaching`) so
  regeneration with `--force` can warn before overwriting them.
